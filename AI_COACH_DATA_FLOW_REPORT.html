UltraSAT · AI Coach · Diagnostic report

What the coach knows, where it looks, and why your practice-exam scores never reach it

Prepared 2026-08-20 · Based on a direct read of the code in apps/api/coach/, apps/web/src/coach/, the exam pipeline, Firestore rules & index config — every claim carries a file reference.

The short answer

The coach is behaving exactly as designed — the problem is that its only source of exam results is a lossy copy, and that copy's delivery pipe is broken in four stacked places. When you finish a practice exam, the app saves a rich, authoritative result (scaled Reading & Writing + Math scores, per-question responses) to users/{uid}/practiceExams — and the coach never reads that collection. It only sees a summary event written to a separate activityEvents stream, and that event (1) most likely never makes it into the coach's context because the query that fetches recent events falls back to an arbitrary, effectively frozen 180-document sample when its required Firestore composite index is missing, (2) gets drowned out by the ~98 per-question events written in the same millisecond, (3) is raced by the results page, which pings the coach before the event is even committed, and (4) even in the best case carries no scaled total and no section scores the coach's context builder will render. On top of that, (5) your target score and exam date genuinely are unset in the profile. So the model — which is explicitly forbidden from inventing data — correctly says: "the score and section breakdown are not available here, so I can't compare this result with your history or a target."

Meanwhile quiz debriefs stay rich and specific because that surface hands the coach a direct pointer (quizId) and the assembler fetches the full quiz document + questions directly — no event stream involved. That asymmetry is the whole story.

1Every input the coach consumes — the complete map

There is exactly one place where everything the coach can possibly "know" is assembled: apps/api/coach/contextAssembler.js (assembleStudentContext). All four coach features — chat, post-quiz debrief, proactive observer notes, micro-lessons — call it, add their own extras (notebook, chat history, trigger reasons), and send the result as text to the model. The model's system prompt then hard-forbids referencing anything outside that text: "You may reference ONLY facts present in the STUDENT CONTEXT below… If the context lacks what you need, say so plainly." That grounding rule is why the coach openly announces missing data instead of guessing.

1.2 — The machinery around the model

Model & prompt. All coach text is generated by OpenAI gpt-5.6-luna (default in config/aiModel.js; no COACH_PRIMARY_* overrides are set in your .env), called through the provider-agnostic modelAdapter.js in JSON mode (your .env pins AI_MODEL=gpt-5.6-luna). Reasoning effort is low for chat, medium for debrief, observer and micro-lessons; routes request 1,200–2,200 output tokens but config/aiModel.js floors the budget at 25k for the reasoning model — brevity is enforced by the prompt's "2–4 sentences" rule instead. The system prompt fixes the persona and the grounding rule, and every reply must be a JSON object containing the message plus up to two actions.

Action sanitizer. Model-proposed buttons are validated server-side: quiz targets must resolve to canonical subcategory ids, links must be on a 9-route allow-list, lessons need a concept or subcategory. Anything else is silently dropped — the coach can never navigate on its own.

Cost & quota guardrails. Every call decrements a per-user daily counter in coachUsage/{uid} and logs token usage to tokenLedger. Daily caps by tier:

Insignificant observer pings are free (no model call). An exhausted quota returns HTTP 429 and a friendly upsell/notice in the UI.

The current implementation hasn't reached that bar: the exam results pages read the authoritative practiceExams store directly, while the coach reads only its own event stream. 4The decisions in front of you

4.1 — The architectural choice

There is one real decision here, and everything else is patching: should the coach's knowledge of exams come from the event stream, or from the authoritative record? The event stream is elegant for derived state (Tier 2 is rebuildable, exclusions work, deletes work), and it should stay the ground truth for skills and habits. But for the headline fact — "this student took an exam and scored X" — you already maintain a perfect, transactionally-saved record in users/{uid}/practiceExams, and the coach's server code (Admin SDK) can read it directly. Fetching the last handful of exam docs in the assembler is one query, immune to F1, F2 and F3 by construction, and it makes the coach agree with the results page by definition — which is exactly the invariant your own design doc demands. My recommendation: Option A + D now, B and C as the durable follow-up, E folded into A.

With that plus a target score, every message in your screenshots becomes possible: score-over-time comparison, section-level diagnosis ("Math is your gap: 390→420 while RW holds"), and target-gap framing — all still fully grounded.

4.3 — Verify before you build (15 minutes)

Four checks, in order of information value:

  • Index: Firebase console → Firestore → Indexes. Look for a composite on activityEvents (userId ASC, clientTs DESC). Absent → F1 confirmed as the active root cause. (The fallback is a silent catch — nothing logs today.)
  • Event volume: count activityEvents where userId == your test account. Over 180 → the fallback sample is frozen for you specifically.
  • Payload: open the newest exam_completed event doc and check payload.scores — expect { readingWriting, math } with no total (F4a) and confirm correctCount/questionCount are sane.
  • Live trace: after fixes, finish one exam and confirm the observer note cites the scaled score; the coach-page "What I know about you" notebook panel (GET /api/coach/notebook) shows whether the result got folded into memory.
